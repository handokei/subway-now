# ADR-001: BFF(Backend for Frontend) 레이어 도입

## 상태

채택됨 (2025-04-14)

## 배경

subway-now 앱은 서울 열린데이터 API를 앱에서 직접 호출하고 있었다.
`EXPO_PUBLIC_` 접두사를 사용하기 때문에 API 키가 앱 번들에 포함되어 빌드 산출물에서 추출할 수 있다.

또한 경로 탐색(ODsay), 장소 검색(Kakao Local) 등 외부 API가 추가될수록:
- 각 API 키가 모두 앱에 노출된다
- 제공자 변경 시 앱 수정 + 스토어 재배포(심사 1~3일)가 필요하다
- 여러 API 응답을 클라이언트에서 조합하면 네트워크 요청이 증가한다

## 결정

별도 BFF 서버(`subway-now-bff`)를 두어 모든 외부 API 호출을 서버에서 처리한다.
앱은 BFF의 통합 엔드포인트만 호출한다.

## 이유

1. **보안**: API 키가 서버에만 존재 → 앱 번들에서 추출 불가
2. **유연성**: 외부 API 제공자 변경 시 서버 파일 1개만 수정 → 앱 재배포 불필요
3. **성능**: 서버 레벨 캐싱(Redis)으로 외부 API 호출 횟수 절감, 클라이언트 네트워크 요청 감소
4. **집약**: 여러 API 응답을 서버에서 조합 후 앱에 최적화된 단일 응답 반환

## 트레이드오프

| 장점 | 단점 |
|------|------|
| API 키 서버 격리 | 서버 운영 비용 발생 |
| 제공자 교체 시 앱 재배포 불필요 | 네트워크 홉 1회 추가 (앱 → BFF → 외부 API) |
| 서버 캐싱으로 비용 절감 | 서버 장애 시 앱 전체 영향 |
| 응답 조합/변환 서버에서 처리 | 초기 개발 시간 증가 |

**완화 전략**:
- 서버 비용: Railway/Fly.io 무료 티어로 시작
- 서버 장애: 앱 내 fallback Provider (직접 호출) 유지
- 네트워크 홉: 캐시 히트 시 외부 API 미호출로 상쇄

## 결과

- 외부 API 변경 시 영향 범위가 BFF 서버 Provider 파일 1개로 한정된다
- 앱은 BFF 엔드포인트의 응답 형식만 알면 되므로, 외부 API의 응답 형식 변경에도 영향받지 않는다
- Factory 패턴으로 `EXPO_PUBLIC_USE_BFF` 환경변수 하나로 BFF ↔ 직접 호출 전환이 가능하다
