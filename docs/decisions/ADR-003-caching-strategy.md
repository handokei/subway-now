# ADR-003: BFF 캐싱 전략

## 상태

채택됨 (2025-04-14)

## 배경

BFF 서버가 외부 API를 프록시할 때, 동일한 요청이 반복되면 불필요한 API 호출이 발생한다.
외부 API는 대부분 호출 횟수에 따라 과금되거나, 일일 한도가 있다.

예시:
- 같은 역의 도착 정보를 여러 사용자가 동시에 요청
- 동일 출발지-목적지 경로를 짧은 시간 내 반복 검색
- 인기 장소 검색어가 반복 조회

## 결정

BFF 서버에 **TTL 기반 캐싱**을 적용한다.
데이터 특성에 따라 차등 TTL을 설정한다.

## 캐싱 규칙

| 데이터 유형 | TTL | 캐시 키 패턴 | 근거 |
|------------|-----|-------------|------|
| 도착 정보 | 15초 | `arrival:{stationName}` | 실시간성 필요, 하지만 15초 미만 갱신은 무의미 |
| 경로 탐색 | 5분 | `route:{from_lat,lng}:{to_lat,lng}` | 대중교통 시간표 기반, 분 단위 변경 |
| 장소 검색 | 1시간 | `place:{query}` | POI 정보는 거의 정적 |

## 캐시 인프라

### 1차: Redis (운영)
- 외부 Redis 인스턴스 (Upstash 무료 티어 등)
- 서버 재시작 시에도 캐시 유지
- 다중 서버 인스턴스 간 캐시 공유

### 2차: In-Memory Map (개발/fallback)
- Redis 연결 실패 시 자동 전환
- 서버 메모리 내 Map + setTimeout으로 TTL 구현
- 단일 서버 환경에서 충분

## 트레이드오프

| 장점 | 단점 |
|------|------|
| 외부 API 호출 횟수 절감 → 비용 절약 | 캐시된 데이터가 최신이 아닐 수 있음 |
| 응답 속도 향상 (캐시 히트 시) | Redis 운영 복잡도 |
| API 장애 시 캐시로 서비스 유지 가능 | 캐시 무효화 로직 필요 |

**완화**: TTL을 데이터 특성에 맞게 설정하여 실시간성과 효율 사이 균형을 맞춘다.
도착 정보는 15초로 짧게, 장소 정보는 1시간으로 길게 설정하여 각 데이터의 변경 빈도에 맞춤.

## 결과

- 동일 역의 도착 정보 요청이 15초 내 중복되면 외부 API 호출 없이 캐시에서 반환
- API 장애 시에도 TTL 내 캐시된 응답으로 서비스 연속성 유지
- 사용자 증가에 따른 외부 API 비용이 선형이 아닌 로그 수준으로 증가
