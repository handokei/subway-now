# ADR-004: 벤더 마이그레이션 경로

## 상태

채택됨 (2025-04-14)

## 배경

현재 앱은 다음 외부 서비스에 의존한다:
- **서울 열린데이터**: 지하철 실시간 도착 정보
- **Kakao Maps**: 지도 렌더링 (WebView HTML 주입)
- **Kakao Local** (예정): 장소 검색
- **ODsay** (예정): 대중교통 복합 경로 탐색

이들은 무료 한도가 있거나 유료이며, 앱 성장 시 비용이 급증할 수 있다.
장기적으로 오픈소스/무료 대안으로의 전환 경로가 필요하다.

## 결정

초기에는 한국 데이터 품질이 높은 상용 API를 사용하되, Provider 패턴으로 추상화하여 점진적 마이그레이션이 가능한 구조를 유지한다.

## 마이그레이션 로드맵

### Phase 1: 상용 API (현재)
빠른 개발, 검증된 한국 데이터 품질

| 기능 | 제공자 | 이유 |
|------|--------|------|
| 도착 정보 | 서울 열린데이터 | 공공 API, 무료 |
| 지도 | Kakao Maps | 한국 지도 데이터 최고 품질 |
| 장소 검색 | Kakao Local | 한국 POI 데이터 품질 |
| 경로 탐색 | ODsay | 한국 대중교통 복합 경로 특화 |

### Phase 2: BFF 서버 도입 (진행 중)
API 키 서버 이전, 캐싱 적용

- 앱 → BFF → 상용 API 구조로 전환
- API 키가 앱에서 서버로 이동
- 캐싱으로 API 호출 횟수 절감

### Phase 3: 오픈소스 전환 (미래)
트래픽 증가 시 비용 최적화

| 기능 | 현재 | 전환 대상 | 비용 |
|------|------|----------|------|
| 지도 | Kakao Maps | MapLibre GL + OSM | 무료 (자체 호스팅) |
| 장소 검색 | Kakao Local | Nominatim (OSM) | 무료 |
| 경로 탐색 | ODsay | OpenTripPlanner + GTFS | 무료 (자체 호스팅) |
| 도착 정보 | 서울 열린데이터 | 유지 (공공 API) | 무료 |

## Provider 전환 절차 (예: Kakao Local → Nominatim)

```
1. NominatimPlaceProvider 구현 (PlaceProvider 인터페이스 준수)
2. BFF 서버에서 Provider 교체
3. A/B 테스트 (일부 트래픽만 새 Provider로 라우팅)
4. 데이터 품질 확인 후 전체 전환
```

앱 코드 변경: **없음**. BFF 서버 파일 1개만 교체.

## 트레이드오프

| 장점 | 단점 |
|------|------|
| 초기에 검증된 데이터로 빠른 개발 | 초기 상용 API 비용 (무료 한도 내) |
| 점진적 전환 가능 (빅뱅 아님) | 오픈소스 데이터 품질이 상용보다 낮을 수 있음 |
| 전환 시 앱 재배포 불필요 | 자체 호스팅 시 인프라 관리 필요 |

## 결과

- 현재: 빠른 개발 속도 확보
- Phase 2: 보안 강화 + 비용 절감 시작
- Phase 3: 트래픽 비례 과금에서 완전 해방 가능

**핵심**: Provider 패턴 + BFF 구조 덕분에 벤더 전환이 "서버 파일 1개 교체"로 축소된다.
이 구조적 결정이 없었다면 벤더 전환은 앱 전체 리팩터링을 의미했을 것이다.
