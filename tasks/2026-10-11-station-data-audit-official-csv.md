### 2-3. id가 인접성을 표현하지 못하는 증거 (독립 출처)

실 API `trainLineNm`의 `"…방면"` 부분은 **그 열차의 물리적 다음 정차역**이다(실 API 152행 중 판정 가능한 137행 전부 `|Δidx|=1`). 비인접으로 나온 2종은 API 오류가 아니라 우리 id 배열의 결함이다:

| API가 인접이라 말한 쌍 | 우리 idx 차이 | 원인 |
| --- | --- | --- |
| 구로 ~ 가산디지털단지 | 21 | `1-100` 번호 사고 (본선 역이 100번대에 단독 배치) |
| 시청 ~ 충정로 | 42 | 순환선 seam (wraparound 미표현) |

군자(능동) 단일 역 검증(실캡처): 7상행 `중곡방면` / 5상행 `장한평방면` / 5하행 `아차산(어린이대공원후문)방면` / 7하행 `어린이대공원(세종대)방면` — **4/4 실제 이웃, 괄호까지 일치**.

단, **분기역에서는 대표 라벨**이다 — 강동(5호선 마천/하남 분기)에서 `마천행`과 `하남검단산행`이 **둘 다 `길동방면`**(길동은 하남 분기). 방면만으로는 분기를 구분할 수 없고 종착역(`bstatnNm`)이 필요하다.

### 3-1. 현재 번호 규약이 3가지로 갈려 있다

| 노선 | 지선/연장 처리 |
| --- | --- |
| 2호선 | `2-105` 까치산 · `2-205` 신설동 — 100번대 **블록** |
| 5호선 | `5-039~046` 마천지선 — **인라인** |

`1-100`이 결정적 증거다 — 가산디지털단지는 지선이 아니라 경부선 본선이다. 중간에 끼울 번호가 없어 100번대로 밀린 것이고, 그 결과가 §2-3의 idx 차이 21이다. **같은 사고가 이미 한 번 일어났다.**

### 3-2. CSV가 분기 소속 데이터를 함께 준다

`선명` 컬럼이 1호선을 분기별로 분리 제공한다 — `1호선(경부선)` 70행 · `1호선(경인선)` 55 · `1호선(광명선)` 39 · `1호선(서동탄선)` 52. 역 추가 시 **분기 소속을 같이 넣을 수 있다**(분기역 판정의 선행 데이터).

### 4-1. 추가 확인 사항

- **GTX-A(`subwayId=1032`)** 가 서울역 조회에 섞여 들어온다. `stations.json` 노선 키 13개에 GTX 없음. **안전성은 확인됐다** — `lineNameBySubwayId('1032')` → `null` → `subwayNm=''` → `matchLine('', line)` → `false`(조용히 드롭, 실행 확인). 버그는 아니지만 GTX-A는 서비스 대상이 아니다.
- **`terminusReachesTarget:1312`** `if (terminusIdx === undefined || targetIdx === undefined) return true;` — 역명이 `stations.json`에 없으면 **fail-open**. 석남(실측 260건)·하남검단산(32건)이 그 케이스라 조기 종착 필터가 그 열차들에 무력하다.
- **`서울` → `서울역` 역명 매핑 부재** — `fromSeoulStationName('서울')` = `'서울'`(실행 확인). 실 API 11건 관측. `seoulStationNameMap` 전체 소비자에 영향이 있어 별도 처리.

## 5. 재발 방지

현재 CI `Data Validation`(`scripts/validate-stations.js`)은 좌표 bounding box와 단조 노선 인접 id 간 haversine sanity만 본다. **엣지 연결성은 검사하지 않는다** — 그래서 9호선 37/37 결손이 계속 통과해 왔다.

역 보강 후 추가할 검증(지금 넣으면 기존 결손으로 즉시 실패하므로 보강과 같은 PR):
1. 노선별 인접 역쌍이 `stationDistances`에 **전부** 존재하는가
2. 순환선 seam(2호선 `2-001`↔`2-043`)이 존재하는가
3. 고립 노드(엣지 0개인 역)가 없는가 — `1-100` 가산디지털단지가 현재 그 상태다
